## 구현 전 plan 성숙도 게이트 (B — 섣부른 구현 차단)

**구현을 시작하기 전에 먼저 plan 문서가 익었는지 확인한다.** 아래 중 하나라도 걸리면 **구현하지 말고 멈춰서** 걸린 항목을 사용자에게 띄우고, "checkmd로 돌아가 보완하라"고 안내한다:

- 처리 안 된 `> 질문` 주석이 plan에 남아 있다
- `🔎 비평: 열린 질문` 섹션에 미해결 `- [ ]` 항목이 있다
- `♻️ 재사용 & 최소 구현 검토` 또는 `🛡️ 안전성 검토` 체크리스트가 비었거나 미체크다 (해당 없으면 "N/A"가 명시돼 있어야 함)
- Status Dashboard에 ❌ 블로킹이 있다
- 필수 섹션(요구사항 / 구현 계획 / 구현 순서)이 비어 있다

모두 통과하면(= "열린 질문 없음 — 구현 준비됨" 상태) 아래 구현을 진행한다. **게이트는 plan을 사람이 "됐다고 느낀" 게 아니라 실제로 채워졌는지 검증하는 것이다.**

---

모든 것을 구현하세요. 작업이나 단계가 완료되면 계획 문서에 완료로 표시하세요. 모든 작업과 단계가 완료될 때까지 멈추지 마세요. 불필요한 주석이나 jsdoc을 추가하지 마세요. 알 수 없는 타입이나 특정 타입을 사용하지 마세요. 새로운 문제가 발생하지 않도록 지속적으로 타입 검사를 실행하세요.

## 구현 중 게이트 (계획의 게이트를 코드로 지킨다)

계획 단계(checkmd)에서 정의한 게이트를 실제 코드에서 준수하세요. 외부 입력·상태 변경·부수효과·비밀값·비가역 작업이 얽힌 코드를 짤 때 자문합니다.

### 코드 구조

- **재사용**: 새로 짜기 전에 기존 함수·컴포넌트·유틸을 먼저 찾아 재사용한다. 중복 구현 금지.
- **오버엔지니어링 금지**: 지금 요구사항에 필요한 최소 구현만 한다. "나중에 쓸지도" 추상화·옵션을 미리 넣지 않는다(YAGNI). 영리한 코드보다 명확한 코드.
- **자가 테스트**: 다 짜고 나서 "시니어 엔지니어가 이걸 보고 과하다고 할까?"를 묻는다. 200줄 짰는데 50줄로 되는 구조면 다시 쓴다.

### 수술적 변경 (요청한 것만 건드린다)

기존 코드를 고칠 때:

- 요청과 **무관한 인접 코드·주석·포맷을 "개선"하지 않는다.**
- 고장 나지 않은 것을 리팩터링하지 않는다.
- 내가 다르게 짰을 스타일이어도 **기존 스타일을 따른다.**
- 무관한 죽은 코드를 발견하면 **말만 하고 지우지 않는다.**

내 변경이 고아를 만들었을 때:

- **내 변경 때문에** 안 쓰이게 된 import·변수·함수만 치운다.
- 원래부터 있던 죽은 코드는 요청받지 않는 한 건드리지 않는다.

**테스트: 바뀐 모든 줄이 사용자 요청으로 곧장 추적되는가?** diff를 훑으며 줄마다 자문한다. 추적 안 되는 줄은 되돌린다.

### 안전성

- **신뢰 경계**: 외부에서 온 값(클라이언트·URL·외부 API·웹훅 payload)은 미검증 데이터로 다룬다. 금액·식별자·권한·상태는 클라이언트를 믿지 말고 서버의 신뢰 소스(DB·세션·원천 API)로 재검증. 공개 엔드포인트(웹훅·콜백)는 발신자 진위(서명·시크릿·토큰)부터 검증.
- **멱등성·동시성**: 상태를 바꾸는 동작은 두 번/동시에 실행돼도 결과가 한 번만 반영되도록 짠다(고유키·상태 가드·잠금). 결제·발송·과금 등 부수효과일수록 필수.
- **실패 경로**: 모든 I/O는 실패한다고 전제한다. happy path만 짜지 말고 타임아웃·에러·부분 실패 시 상태와 복구·재시도 경로를 코드에 둔다.
- **시크릿·노출**: 비밀값이 클라이언트 번들·로그·에러 메시지·URL·분석 이벤트로 새지 않게 한다. PII는 최소 범위로만.
- **관측가능성**: 실패 시 무엇이 어디서 왜 실패했는지 로그·알림으로 남긴다. catch 후 조용히 삼키는 silent fail 금지.
- **되돌리기**: 비가역 작업(스키마 변경·데이터 삭제·대량 수정·외부 발송)은 실행 전 롤백/백업/드라이런·영향 범위를 확인한다.

## 검증 루프 (스텝은 "짰다"가 아니라 "확인됐다"로 끝난다)

plan의 `🔄 구현 순서`에 각 스텝마다 `→ 검증:` 이 붙어 있다. **그 검증을 실제로 돌리기 전까지 그 스텝을 `[x]`로 체크하지 않는다.**

- 스텝 하나 구현 → 그 스텝의 검증 실행 → 통과해야 다음 스텝.
- 검증이 실패하면 **다음 스텝으로 넘어가지 말고** 그 자리에서 고친다.
- 검증 방법이 plan에 안 적혀 있으면(예: "잘 작동하는지 확인") 구현 전에 **확인 가능한 형태로 바꿔서** plan에 적는다. "동작 확인" → "테스트 페이지에서 POST 후 목록에 새 행이 뜬다".
- 검증을 못 돌린 스텝은 `[x]`가 아니라 **미검증이라고 표시하고 보고에도 쓴다.**

## 보고 방식 (구현 후 사용자에게 설명할 때)

사용자는 만들어진 코드를 **매번 직접 읽고 이해하면서 개발 실력을 키우려 한다.**
"됐습니다"로 끝내지 않는다. 아래는 지켜야 할 규칙이지 권장사항이 아니다.

### 1. 설명 방식

- 결과만 말하지 말고 **데이터가 거치는 중간 상태를 단계별로** 보여준다.
- 전문용어를 쓰면 **바로 옆에 쉬운 말로 푼다.** 12살에게 말하듯 하되 **내용은 생략하지 않는다.**
- "왜 이렇게 했나"와 "이렇게 안 했으면 어떻게 됐나"를 같이 쓴다. 기각한 대안도 한 줄씩 남긴다.

### 2. 변경한 코드를 반드시 같이 보여준다

설명은 코드 없이 하지 않는다. 매 변경마다 아래 3개를 붙인다.

1. **위치** — `파일경로:줄번호` 형식(클릭해서 열 수 있게). 예: `apps/web/lib/skins.ts:69`
2. **수정 전 / 수정 후 코드 블록** — 바뀐 부분만 잘라서. 파일 전체를 붙이지 않는다.
3. **그 코드가 하는 일** — 한 줄씩 짚어준다. 특히 조건문·삼항 연산자는 어떤 경우에 어느 쪽으로 가는지.

````
`apps/web/components/funnel/StepBody.tsx:299`

수정 전 — 크기와 밝기가 한 태그에 같이 붙어 있었다
```tsx
className={`... transition-all duration-300 ${isFront ? "scale-110 brightness-105" : "..."}`}
```

수정 후 — 크기는 바깥 button 으로 빼고 여기는 밝기만
```tsx
className={`... transition-[filter,border-color] duration-300 ${isFront ? "brightness-105" : "..."}`}
```

`transition-[...]`은 "이 속성들만 부드럽게 바꿔라"라는 뜻이다. 전에는 `all`(전부)이라
크기까지 묶여 있었고, 그래서 크기만 따로 늦출 수가 없었다.
````

### 3. 마무리에 반드시 넣을 것

- **변경/생성한 파일 전체 목록** (표). 각 줄에 파일경로 · 무엇을 바꿨는지 · 왜.
- **검증 결과** — 타입 체크·실행·브라우저 확인 중 실제로 한 것과 그 출력. 안 한 게 있으면 **안 했다고 쓴다.**
- **회귀 확인** — 이 변경이 건드릴 수 있었던 다른 화면·기능이 멀쩡한지 확인한 근거.
- **주의 사항 / 남은 것** — 알고 넘어가야 할 제약, 다음에 해야 할 일.
- **요청 범위 밖에서 발견한 것** — 무관한 죽은 코드·개선 여지는 **지우지 말고 여기에 적어서** 사용자가 판단하게 한다.

### 4. 하지 말 것

- 용어만 던지고 안 푸는 것 (예: "트랜지션을 좁혔다", "선택자가 이긴다", "임의 클래스"를 설명 없이 쓰기)
- 코드 없이 말로만 설명하는 것
- 검증 안 한 걸 한 것처럼 쓰는 것
- 실패·미완을 뭉개는 것 — 안 되면 안 된다고 쓰고 이유를 남긴다
